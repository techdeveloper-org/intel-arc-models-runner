## ADR detail: performance programme (DL-061..DL-070)

Status of all ten: proposed on 2026-10-29 as part of plan section 23 and revised in v8.4 after four independent reviews (G1 faithfulness, G2 architecture, G3 tests, G4 performance; defects and resolutions in plan 23.9.1); no source changed; effective when the named work package is accepted. Evidence ids (P1-P5, L-nn, H-nn) name rows of the **register in plan section 23.3, which is the durable copy**; the discovery reports P1-P5 themselves are an uncommitted session scratchpad, so a P-id here is a pointer into the register, not a reference to a file a later session can open. Evidence class is stated per claim (PROVEN, READ, READ+replica, DERIVED, HYPOTHESIS). Work packages are WP-nn in plan section 23.5.2; design items CC-n are in plan 23.5.0. Numeric defaults named below (timeouts, sizes, TTLs) are policy constants, not measurements.

### DL-061 Shared async bridge (WP-03)
- Context: blocking load, compile, generate, tokenize, embed, GGUF parse and pull run inside `async def` handlers; a replica probe that needs about 52 ms took 2077 ms while one 1 s load plus 1 s generate ran (P4-01, READ+replica). The streaming bridge calls `call_soon_threadsafe(queue.put_nowait)` from a thread, which never raises `QueueFull`, so the retry branch is dead and the sentinel can be dropped; the replica lost 67 of 300 tokens under a 2 s loop stall (P4-03, READ+replica). A disconnected client leaves the worker generating (P4-04, READ+replica). The bridge is copied three times. The engine's `generate_stream` already starts its own inner thread, blocks on bounded `chunk_queue.put` calls from the callback and the worker `finally`, and reads its cancel flag only inside the callback (`openvino_engine.py:299, 323, 328, 334-347`, READ, verified by reviewer G2 and re-read in v8.4). Prefill is not cancellable (READ). Whether concurrent `LLMPipeline.generate` calls are safe is a HYPOTHESIS decided by N-03. The per-token bridge cost was measured at 3.7 us (JSON plus timestamp, replica) against 24.9 ms per GPU token (DERIVED), so the bridge is not a throughput lever.
- Options: (A) one helper, dedicated executors, FIFO admission, an ordered channel and a cancel/join protocol (CC-1..CC-4); (B) a helper that blocks the producer until the loop has accepted each chunk (P1-03 option 2); (C) bare `to_thread` keeping three bridges; (D) one helper with an interim `threading.Lock` per engine until the lease exists.
- Decision: A. Two private named executors (`inference`, `load`) are used only after an async FIFO grant, so waiting never occupies a thread; one executor thread per stream iterates the generator beside the engine's inner pipeline thread (the two are not folded; collapsing them is WP-16); chunk, `done` and `error` are all delivered through `call_soon_threadsafe` so order is call order, and the consumer drains until `done and buffer empty`; the cancel event is a parameter of `generate` and `generate_stream`, checked in the callback and the wait loop; inner-thread puts time out and re-check the cancel event or the queue has no limit (growth bounded by `max_new_tokens`, `le=32768`); the generator's `finally` sets cancel and **joins the inner thread** before the bridge releases the lease and the engine grant; a `client_stall_timeout` cancels a consumer that stops draining; non-stream generate uses the same cancellable callback path; `copy_context().run` carries the request id into both threads; mid-stream failures use the SSE/NDJSON error event of CC-11. The admission-time lease and evict-skip (CC-4) ship in this package because offloading makes eviction mid-generate newly possible. N-02 runs before the package is merged; whether a separate disconnect watcher is still needed is decided by a replica test of the installed Starlette.
- Consequences: one place to test loss, cancel and ordering; routes shrink; a slow client no longer slows generation and a stalled one is cancelled; concurrent requests to one model wait FIFO, as the single compute engine does anyway; prefill is not interruptible and the tests say so; per-stream worst-case buffer is a computed number in the stage record.
- Reversibility: high in isolation (helper is additive, executors private), but valid only in reverse dependency order once WP-04, 05, 14 and 15 exist (CC-13). No ABI or data format involved.
- Source: register rows P4-01, P4-03, P4-04, P4-12; CC-1..CC-4.

### DL-062 Manager concurrency model (WP-03, WP-04, WP-05)
- Context: `ModelManager._lock` is held across path resolution, eviction, `unload()` and compile, and shared with `record_generation_metrics`, `get_telemetry` and listing (`model_manager.py:133-167`; P4-02, P1-02, P5-03, READ). First-request cost after load is PROVEN (P3-03: CPU TTFT 9.0-14.2 s vs 0.07-0.36 s steady; GPU 134-221 ms vs 20-74 ms); compile duration itself is a HYPOTHESIS (P4-02 "O(10-100 s)", unmeasured). The engine returns one shared object to all callers with one mutable `_telemetry` (P4-05, P1-11, READ); eviction sets `_pipeline=None` under an in-flight request (P4-05, P5-02, READ); every caller of `get_or_load_*` is unleased (`routes_openai.py:167`, `routes_ollama.py:286, 385`, `routes_embeddings.py:52, 92, 146`, `routes_ui.py:389`, `audio_worker.py:211`, `runner.py:117`, `cli/main.py:163`; READ); the cache key uses the raw string and includes gamma and eviction precedes a load that may fail (P4-06, P1-06, READ). Two simultaneous compiles double peak memory on a 6976 MiB shared ceiling (probe PROVEN, effect HYPOTHESIS).
- Options: (A) keep one lock, move scans and unload outside it; (B) CC-3..CC-7 (admission-time lease released by the finishing thread, single flight with shielded waiters, sorted compile slots and failure TTL, hard capacity limit with FIFO capacity queue and timeout, lock hierarchy with `_state_lock` a leaf); (C) one asyncio manager task owning all lifecycle through a queue (cleanest, rewrites the synchronous API the CLI uses).
- Decision: B, with the sync API kept and an async variant added. The lease counter is taken at admission in the same critical section as the cache lookup and released by the worker thread that finishes (never by the awaiting coroutine), so a queued request pins the engine and a cancelled `run_in_executor` cannot leave a running thread unleased; a request holds at most one lease and acquires two in sorted key order; the load runs detached on the `load` executor and waiters await a shielded future, so one cancelled client never cancels the compile; compile slots are taken in sorted device order and a failed load is remembered for a short policy TTL; the resident count never exceeds `max_loaded_models`, a pending load waits on a condition with a timeout and fails with `EngineBusyError` (HTTP 503 + `Retry-After`); `unload()` and native `close()` run outside `_state_lock` and only at `leases == 0`; the cache key is resolved path + device + draft path + draft device + gamma (gamma leaves the key only in WP-13, DL-068). Serialization per engine is the default because concurrent `LLMPipeline.generate` safety is a HYPOTHESIS (N-03 decides whether it is mandatory or merely conservative; the default does not change either way). `warmup_on_load` ships off and flips only on a committed N-04 result judged as a distribution, including the wait on warmup, within the same budget reservation.
- Consequences: cache hits and telemetry no longer wait behind a compile; same-key requests share one compile; compiles stay sequential per device; request latency under contention rises and correctness rises with it; unload of a leased engine waits or raises `EngineBusyError` (409); telemetry stays additive (`generate_ex`, final `TokenChunk`, `get_telemetry()` last-value for one release); a new read-only `GET /api/ps` shows residents and the cache root.
- Reversibility: medium. State is in memory only, but reverting WP-04 or WP-05 is valid only in reverse dependency order (CC-13).
- Source: register rows P4-02, P4-05, P4-06, P5-02, P5-03, P1-02, P1-06, P1-11; CC-3..CC-7, CC-10.

### DL-063 Memory budget and request limits (WP-06, WP-07)
- Context: three LRU caches are each capped at two by count with no byte accounting, and image, video and audio engines are built outside the manager (`audio_worker.py:219`, `cli/main.py:908, 964`) (P5-01, READ); the probe shows a 6976 MiB shared ceiling (PROVEN) and `free_mb` null for the iGPU, and on this machine the iGPU, NPU and CPU draw from one host pool, so a per-device budget would let each take the whole fraction. Image and video requests have no pixel or frame budget; the derived unfused-attention score-tensor bound is 0.54 GB at 512x512, 2.72 GB (2592 MiB) at 768x768 and 8.59 GB (8192 MiB) at 1024x1024; 2.72 GB is below 6976 MiB on its own and R09 reaches "consistent with the recorded 768 failure" only by adding a second softmax buffer, weights and the VAE and by assuming SDPA is not fused, which is unverified (P5-04, DERIVED/HYPOTHESIS). The SD-1.5 failure has no committed result row (P3-12) and no passing size is recorded. Auto-downscale changes output silently (P5-04 option C), which the project forbids. `VRAMExhaustedError` (HTTP 507, code `VRAM_EXHAUSTED`) already exists in `core/exceptions.py:108-120`.
- Options: (A) fail-closed static budget and limits from configuration, typed errors, nothing evicted when a model alone exceeds the budget; (B) calibrated per-model-class factors produced by a measurement run and shipped with the result files; (C) one engine per device with sequential loading, documented as the iGPU profile.
- Decision: A now as mechanism (CC-8): the budget is per **memory domain** (`shared_host` here), the registry covers every engine kind or a `register_external` footprint, admission **reserves** bytes under `_state_lock` before compiling, bytes are credited back only when the engine's finalizer fires (eviction frees nothing while a call frame holds the pipeline), and every number carries a `basis` (`measured`, `convention`, `unaccounted`); a model larger than the whole budget raises the existing `VRAMExhaustedError` with nothing evicted; a model that fits only by evicting leased engines takes the CC-6 wait/timeout path; a runtime allocation failure is never converted into a CPU fallback. B as data once N-10, M-07 and M-25 results are committed, C as a documented profile. No default numeric limit and no calibration factor is shipped before its result file exists; an unset limit warns once and does not reject; structural checks ship enforced. The on-disk-bytes factor is labelled a convention until replaced. Enforcement flag is off at first.
- Consequences: loads that used to succeed may be refused once enabled; no guessed numbers in the repository; the first release of the mechanism protects only users who configure limits; `GET /api/ps` reports `resident`, `pending_release` and `reserved`. Provisional answers (maintainer may override): warn-once for limits (question 1), keep CPU fallback default but always record it and never fall back on resource exhaustion or context loss (question 2), keep 507 for budget-exceeded (question 8).
- Reversibility: high. Limits and the budget are configuration and a flag.
- Source: register rows P5-01, P5-04, P5-05, P5-15, P5-16, P5-17; CC-6, CC-8, CC-11.

### DL-064 Prefetch and advice strategy (WP-08, WP-09, WP-10)
- Context: the native path performs no I/O in "prefetch" without stager or pin (P2-02, READ); a synchronous-wait expiry (1.5 s default, max 1900) marks the context dead and disables staging for the manager's life (P2-03, READ); that cold source pages fault inside the timed copy depends on whether the driver reads pageable sources at Execute or Append, or rejects them, and is a HYPOTHESIS (P2-03b; N-07 decides); layer 0 of the next token is never prefetched, a thread is created per prefetch, and depth is 1 of R-1 (P2-07, READ); the ring is direct-mapped by `layer % R` (`weight_streamer.py:324`), so with N mod R != 0 a cyclic window across the wrap targets a slot in use (G2 B9, verified), `release_layer_slot` has no caller in the engine, and `RingSlots.tla:7` states there are no pin counts (READ); the Windows open uses `FILE_FLAG_RANDOM_ACCESS` (`arc_flash_stream_mmap.c:168`, effect HYPOTHESIS); Windows is the supported platform (DL-035). A cyclic scan over N>R layers misses every layer under any replacement policy (P2-07), consistent with DL-008 and DL-045. **No served model uses the streamer** (L-12: `model_manager.py:107-167`; the engine is created only by `run-heavy`, `cli/main.py:1473`, and emits tokens from a fixed list, `flash_stream/engine.py:156-178`); no native or flash-stream result exists, so every size of effect is a HYPOTHESIS.
- Options: (A) Python-level pre-fault of the registered tensor ranges before the timed copy, wrap-around prefetch, a persistent worker, ring slots by access sequence with holders, no ABI change; (B) a native `arc_mmap_advise` now (ABI per DL-066); (C) raise the sync timeout (rejected: clamped below the driver TDR by design, DL-051).
- Decision: A first, measure-first, behind `ARC_PREFAULT` default off until N-07 passes a stop rule recorded before the data is read (lower CI bound of cold-read GB/s with pre-touch above the upper CI bound without); B only if A does not recover the cold-cache cost on Windows. Keep a direct-mapped ring but assign slots by access sequence (`seq mod R`) with per-slot `holders`; a slot is overwritable only when `holders == 0` and it is not PENDING; the engine consumer gains acquire/release; prefetch depth is capped so it never targets the consumer's slot; R=1 disables prefetch; `RingSlots.tla` gains `holders`, the release action and `NoEvictWhileHeld`/`DeadlockFree` with constants chosen so N mod R != 0. WP-08..WP-10 are not scheduled until a committed N-07/N-08/N-09 result passes a pre-registered gate, because they change only the `run-heavy` CLI path (question 9).
- Consequences: no DLL rebuild for stage 1; the flag keeps behaviour identical until measured; TLC must be re-run locally (reported NOT RUN in the cloud); a Python pre-touch burns a CPU thread and gives no asynchronous kernel readahead (P2-02 option 3 trade-off); the consumer loop becomes a holder protocol (a protocol change, not an eviction-rule tweak).
- Reversibility: high for A (flag and commit revert); B is covered by DL-066.
- Source: register rows P2-01..P2-10, L-12; CC-9.

### DL-065 Cache unification (WP-12a, WP-12b)
- Context: `CACHE_DIR` is set only for GPU and relative to the working directory (`openvino_engine.py:155-158`, P1-08, READ); NPU, CPU, the speculative target and draft, and every non-LLM pipeline get no properties (P1-08, P5-07, READ); `AOTCompilationManager` writes `~/.arc-runner/cache/blobs/<DEV>/<model>`, so an AOT compile does not warm what engines read (P5-07, READ); `warm_load_time_ms` is a constant on failure (P5-08, READ, honesty). First-call cost is PROVEN (P3-03: CPU 9.0-14.2 s, NPU 2.5-4.9 s, GPU 134-221 ms). NPU TTFT is a flat 2.23-2.27 s across prompt lengths (P3-02, PROVEN); its cause (static padded prefill) and whether a cache removes it are HYPOTHESES. For NPU and CPU, cold versus warm differs by OS page cache only until the cache is set (N-04).
- Options: (A) one absolute cache root with a device-keyed layout used by every engine and by the AOT manager; (B) keep GPU-only but make it absolute; (C) do nothing but record cold load time; (D) A, split so the engine part lands first.
- Decision: D. WP-12a (engine only, no manager dependency, scheduled right after WP-02) sets an absolute, CWD-independent, device-keyed `CACHE_DIR` for GPU, NPU and CPU from `ARC_CACHE_DIR` or `DEFAULT_CACHE_DIR / "ov_cache"`, keeps the user-supplied override, degrades with a logged reason when unwritable, and is bracketed by N-04 before and after; WP-12b (after WP-05) extends it to every pipeline type, the speculative target and draft and the AOT manager, derives `cache_hit` from a before/after listing and refuses a purge while any engine holds a lease. NPU static-shape properties (`MAX_PROMPT_LEN`, `MIN_RESPONSE_LEN`, `GENERATE_HINT`) are decided by the M-19 sweep in WP-17, never shipped on a guess; property names are verified against the installed device's supported list and a wrong name raises.
- Consequences: one directory to warm, size and purge; every load path changes (medium risk, hence two steps); stale-blob behaviour after driver or OpenVINO updates is a HYPOTHESIS and a LOCAL test; sharing a directory between two processes keeps device-keyed subdirectories because OpenVINO's locking is unverified.
- Reversibility: high. Cache directories are disposable and the change is a helper plus call sites.
- Source: register rows P1-08, P5-07, P5-08, P1-02, L-03.

### DL-066 ABI policy and the native window (WP-10)
- Context: CLAUDE.md says to bump `ARC_NATIVE_ABI_VERSION` in four places when an exported function changes, and any change under `native/*.c|h` needs the rebuilt `.so`, `.dll` and sidecars in the same commit (DL-040); the Windows DLL cannot be rebuilt in the cloud, so **every** C change costs a local rebuild whether or not an export changes (reviewer G2; the earlier claim that internal changes avoid the cost was wrong). Candidate exports from P2: `arc_mmap_advise` (P2-02), `arc_mmap_get_layer_ptrs` and `arc_ze_dma_copy_batch` (P2-08 option 3), `arc_ze_host_copy` (P2-06 option 2), immediate-list submit and wait (P2-05 option 3). Internal candidates: memmove out of the spinlock (P2-06 option 3), a layer index table (P2-08 option 2), a copy-only queue ordinal found internally (P2-05 option 2). Moving the memmove out of `arc_table_lock` changes when `arc_ze_free` may complete relative to an in-flight copy, a behavioural-contract change of an existing export. The four ABI strings are `arc_flash_stream_mmap.h:37`, `bridge.py:33`, `build_native.py:19` and `arc_flash_stream_mmap.c:486`; the descriptor layout check is 184/11792 bytes (`bridge.py:68-69`). The Python side of per-tensor overhead was replica-measured at 2.95-11.09 us per tensor (P2-08) and is small against I/O and DMA. No native or flash-stream result exists and no served model uses the streamer (L-12).
- Options: (A) bump per export as each is justified; (B) one native window: internal and export changes together, one rebuild, bump only per the policy below; (C) never change the C ABI, only Python.
- Decision: B. Policy: bump only for a change of signature, of struct layout or of the documented behavioural contract of an existing export; a **new export with unchanged existing signatures is backward compatible** when the bridge probes it individually with `getattr(dll, name, None)` and degrades to the Python path when it is absent, so a stale library keeps working; the build info gains `contract=<n>` (the bridge must parse by key; verified when the window starts) so the bridge and tests can assert the contract revision; the four ABI strings are checked by one script test. The memmove item is a contract change, so the window bumps to ABI 4 unless that item is dropped. Each item is built only if its own committed measurement (N-07, N-08, N-09) passes a gate recorded before the data was read; an export with no supporting measurement is not added. A TSan build of the harnesses is added for the memmove change. The former WP-11 id is retired into WP-10.
- Consequences: one local DLL rebuild per window; hardware numbers gate native work; if nothing is justified the ABI never changes; a stale library still falls back to the Python path in both directions (ABI 3 library with an ABI 4 bridge, and the reverse).
- Reversibility: medium. Reverting the commit restores ABI 3; the ABI check prevents a mixed state from loading and the bridge falls back to Python until the DLL is rebuilt.
- Source: register rows P2-02, P2-05, P2-06, P2-08, L-12; CC-12.

### DL-068 Speculative decoding gate (WP-13)
- Context: committed same-model data (qwen-2.5-1.5b on both devices, medium tier medians 41.42 tps GPU and 14.67 tps NPU) gives a per-step time ratio **c = t_draft_step / t_target_step = (1000/14.67) / (1000/41.42) = 68.2 ms / 24.1 ms = 2.82** (P1-07, DERIVED). c is a ratio of times, not of tokens per second, and 2.82 is for the same 1.5B model on both devices, so it is not evidence about a smaller draft (UNMEASURED) and must not be used against NPU drafting in general. Model (a model, not a measurement): per round the draft takes g steps and the target verifies g+1 tokens in v >= 1 target steps, giving S = (1 - a^(g+1)) / ((1 - a)(g*c + v)) for acceptance a; (g+1)/(g*c+1) is its **upper bound at a = 1 and v = 1** (at c = 2.82, g = 4: 5/12.28 = 0.41), and S > 1 there iff c < 1. c < 1 is **necessary for any a** (the geometric sum is at most g+1) but **not sufficient**, because a < 1 and v > 1 only lower S. On a shared-DRAM iGPU a draft on NPU or CPU and a target on GPU contend for one memory bus, so c measured with the other device idle is optimistic. Prompt-lookup decoding needs no second model (c close to 0 by construction; `GenerationConfig.is_prompt_lookup` exists in the installed GenAI 2026.4.1) and is not considered by the engine. No speculative result exists. The engine ignores the requested device (P1-05, P5-13, READ), recompiles when gamma changes, has dead dynamic-gamma code (`_adapt_gamma`, no caller), and bakes gamma at load (`speculative_engine.py:260`), and the draft can silently fall back to CPU (P1-07, P5-13, READ). Acceptance and speed-up are reported as 0 and 1.0 until measured (DL-036).
- Options: (A) leave speculative decoding enabled and add a warning; (B) gate it on a committed calibration whose measured speed-up has a lower confidence bound above 1 under the stats module, with c < 1 as a precondition; otherwise fall back to the plain target with a clear log; (C) default the draft to GPU or CPU and leave NPU experimental.
- Decision: B. The binding condition is the measured speed-up's lower confidence bound above 1 for that target, draft and device; c < 1 only screens out hopeless configurations. No acceptance rate is ever inferred; the dead gamma code is deleted unless the pipeline exposes counters. Gamma leaves the cache key and `num_assistant_tokens` becomes a per-request parameter **in WP-13 only**, in one commit with the engine change (WP-05 keeps gamma in the key, otherwise a request for gamma 6 would silently receive gamma 4). Provisional policy (question 3, maintainer may override): refuse and fall back, with `draft_device` and `speculative_calibrated=false`, when speculative decoding is enabled implicitly or by config default; honour an explicit per-request or per-model operator request with a warning and `speculative_calibrated=false`. N-16 gains a prompt-lookup arm and a contention arm.
- Consequences: speculative decoding is off by default for any model without calibration; docs lose any NPU-draft speed-up wording that lacks a result file (H-15); one new workload `llm_speculative` and a hardware calibration run (N-16) are needed before it can be enabled.
- Reversibility: high. The gate is a pre-check on enabling.
- Source: register rows P1-05, P1-06, P1-07, H-15, H-16, L-06; CC-10.

### DL-069 Decode-throughput and first-request levers (WP-12a, WP-17)
- Context: decode owns wall time (P3-01, PROVEN: TTFT is 0.52 % and 0.98 % of GPU latency at the medium and hard tiers), GPU decode is implied bandwidth-bound (P3-09, DERIVED 37.7-49.0 GB/s), the NPU TTFT is a flat 2.23-2.27 s (P3-02, PROVEN), CPU CV is 11.1-38.0 % (P3-05, PROVEN) and the first call costs CPU 9.0-14.2 s, NPU 2.5-4.9 s (P3-03, PROVEN). Yet no earlier row targeted bytes per token or tokens per step: a grep of `src/`, `scripts/` and `scratch/` finds none of `ENABLE_CPU_PINNING`, `SCHEDULING_CORE_TYPE`, `INFERENCE_NUM_THREADS`, `ENABLE_HYPER_THREADING`, `DYNAMIC_QUANTIZATION_GROUP_SIZE`, `ATTENTION_BACKEND`, `MAX_PROMPT_LEN`, `MIN_RESPONSE_LEN`, `GENERATE_HINT`, `CACHE_MODE`, `SchedulerConfig`, `start_chat` or prompt lookup (READ). KV precision is settable by the env var `ARC_KV_CACHE_PRECISION` (`openvino_engine.py:42, 161-163`) but is measured for quality only (M-15). `start_chat`/`finish_chat`, `SchedulerConfig.enable_prefix_caching`/`dynamic_split_fuse`/`cache_size` and `GenerationConfig.is_prompt_lookup` exist in the installed GenAI 2026.4.1, and the CPU property names `INFERENCE_NUM_THREADS`, `SCHEDULING_CORE_TYPE`, `ENABLE_HYPER_THREADING`, `ENABLE_CPU_PINNING`, `KV_CACHE_PRECISION` and `DYNAMIC_QUANTIZATION_GROUP_SIZE` were verified against the installed OpenVINO 2026.4.1 CPU plugin's `SUPPORTED_PROPERTIES`; GPU and NPU property names (`ATTENTION_BACKEND`, `CACHE_MODE`, `MAX_PROMPT_LEN`, `MIN_RESPONSE_LEN`, `GENERATE_HINT` and the GPU forms of the rest) are unverified on the cloud VM. The effect of every lever is a HYPOTHESIS.
- Options: (A) schedule by discovery-report order (correctness packages first, levers later); (B) measurement-first levers placed right after instrumentation, with the engine cache fix first because its first-call cost is PROVEN; (C) ship vendor-recommended property defaults now.
- Decision: B. WP-12a and WP-17 follow WP-02 and precede WP-08..WP-10. Each sweep (M-10 CPU, M-17 GPU properties and KV precision, M-18 weight format, M-19 NPU static shapes, M-23 stateful chat and prefix caching, M-24 `CACHE_MODE`, M-26 prompt lookup) runs through `--ov-prop`/`--gen-opt` (WP-02i), which print the device's supported properties and refuse unlisted keys. **Pre-registration:** the decision rule and any magnitude threshold are recorded in a DL entry before the sweep's data is read (default rule: lower CI bound of the benefit above the control's upper CI bound under `benchmark/stats.py`, plus `bench_kv_quality` showing no divergence for KV precision). Adopted defaults live in `core/ov_property_defaults.json`, each entry citing a committed result file; nothing else sets a default. A prompt longer than an NPU prompt cap raises a typed error, never truncates. Stateful chat is a session design with its own DL entry only if M-23 is positive.
- Consequences: the only packages that can change a proven bottleneck come early; no property default exists without a result; the programme gains ten measurement requests (M-17..M-26) of which M-20 is already closed by code reading; WP-03..WP-07 are explicitly labelled correctness work, not throughput work.
- Reversibility: high. An empty defaults file restores today's behaviour.
- Source: register rows L-01..L-11; G4.

### DL-070 Test infrastructure for the programme (WP-02h and all packages)
- Context: `tests/conftest.py` holds only hardware fixtures (`hardware_flag`, `live_topology`, `require_intel_gpu`, `require_intel_npu`); existing fakes are ad hoc (`MagicMock` via `patch.dict("sys.modules")`, `TestClient` over a tmp model dir, `FakeClock`, the C-side `fake_ze_loader.c`); `MagicMock` cannot give deterministic interleavings; no TSan harness exists (`mmap_harness.c` builds with ASan and UBSan, `ze_harness.c` with no sanitizer); the plan listed no test names; sanitizer, fake-loader and mingw-compile work had been labelled LOCAL (G3, verified).
- Options: (A) ad hoc mocks per test, wall-clock thresholds; (B) shared controllable fakes, event-gated ordering, concrete names, an evidence slot per package, a separate `integration` marker, CLOUD/LOCAL by what runs where.
- Decision: B. WP-02h delivers `FakeEngine` (event gates, `raise_on`, `declared_bytes`, cancel-honouring generate, close counter), a fake `ov_genai`, a fake Sysman and a Python-level fake Level Zero loader as fixtures in `tests/conftest.py`; WP-01f is the only WP-01 item that depends on it. CLOUD means no Intel silicon and no Windows needed (fakes, gcc `-Werror`, ASan/UBSan/TSan, the fake loader, a mingw compile that is not run); LOCAL means the maintainer's machine (Windows runtime, DLL rebuild, TLC, real silicon, external tools).
- Consequences: a fixtures package must land before WP-01f and WP-03; property and stress tests with seeded interleavings are added for the lease, manager and ring invariants; a skipped test can never be mistaken for a pass.
